# Networking and the Database

Until now the database lived next to the application: in Docker Compose on your
laptop, and in a temporary container in CI. A real deployment needs a database
that survives restarts, is backed up, and is **not reachable from the
internet**. In this chapter you build the network the rest of the book runs in,
a VPC with public and private subnets, and put a managed PostgreSQL database
(Amazon RDS) in the private part. The password is generated by AWS and stored
in Secrets Manager, so it never appears in your code, your state, or your
terminal.

## The idea

A **VPC** (Virtual Private Cloud) is your own private network inside AWS. You
divide it into **subnets**, and each subnet lives in one **Availability Zone**
(AZ), which is one data centre (or a group of them) in the region.

What makes a subnet "public" or "private" is not a setting on the subnet. It is
the **route table** attached to it:

- A **public subnet**'s route table sends internet traffic (`0.0.0.0/0`) to an
  **internet gateway**. Load balancers and servers that must be reachable go here.
- A **private subnet**'s route table has no such route. Nothing in it can reach
  the internet, and the internet cannot reach it. The database goes here.

```text
 Region eu-central-1        VPC 10.0.0.0/16
 ┌───────────────────────────────────────────────────────────────┐
 │                         Internet gateway                       │
 │                               │                                │
 │   AZ eu-central-1a            │            AZ eu-central-1b    │
 │  ┌──────────────────────┐     │      ┌──────────────────────┐  │
 │  │ public 10.0.1.0/24   │◀────┴─────▶│ public 10.0.2.0/24   │  │
 │  │ (servers, ALB)       │            │ (servers, ALB)       │  │
 │  └──────────┬───────────┘            └──────────────────────┘  │
 │             │ port 5432, inside the VPC only                   │
 │  ┌──────────▼───────────┐            ┌──────────────────────┐  │
 │  │ private 10.0.11.0/24 │            │ private 10.0.12.0/24 │  │
 │  │ RDS PostgreSQL       │            │ (standby AZ for RDS) │  │
 │  └──────────────────────┘            └──────────────────────┘  │
 └───────────────────────────────────────────────────────────────┘
```

Two decisions shape this design:

- **Two AZs, even for a single database.** RDS refuses a subnet group that
  covers only one AZ, and an EKS cluster (Chapter 10) needs subnets in at least
  two. Subnets are free, so you create both from the start.
- **No NAT gateway.** A NAT gateway would let the private subnets reach the
  internet (for updates, for example), but it costs about $35 per month per AZ
  plus data charges, and the database does not need the internet. Everything
  that does (the k3s server, EKS nodes) runs in the public subnets, protected
  by security groups. Production setups usually put the servers in private
  subnets behind a NAT gateway; the Lessons Learned chapter comes back to this.

## Step 1: Plan the address space

A CIDR block such as `10.0.0.0/16` describes a range of addresses: the number
after the slash says how many leading bits are fixed. `/16` leaves 16 bits free
(65,536 addresses), `/24` leaves 8 bits (256 addresses, of which AWS reserves 5
in every subnet).

| Network | CIDR | Addresses |
|---|---|---|
| VPC | `10.0.0.0/16` | 10.0.0.0 – 10.0.255.255 |
| public, AZ a | `10.0.1.0/24` | 10.0.1.0 – 10.0.1.255 |
| public, AZ b | `10.0.2.0/24` | 10.0.2.0 – 10.0.2.255 |
| private, AZ a | `10.0.11.0/24` | 10.0.11.0 – 10.0.11.255 |
| private, AZ b | `10.0.12.0/24` | 10.0.12.0 – 10.0.12.255 |

The numbering is a convention for humans: single digits are public, `1x` is
private. Leaving gaps makes it easy to add more subnets later without
renumbering. Pick a range that does not overlap with networks you might connect
to one day (your office VPN, another VPC); overlapping ranges cannot be peered.

## Step 2: The network (`network.tf`)

Create `infra/terraform/network.tf` and paste the whole file:

```hcl
locals {
  name = "rust-devops"

  azs                  = ["eu-central-1a", "eu-central-1b"]
  public_subnet_cidrs  = ["10.0.1.0/24", "10.0.2.0/24"]
  private_subnet_cidrs = ["10.0.11.0/24", "10.0.12.0/24"]
}

resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = { Name = "${local.name}-vpc" }
}

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id

  tags = { Name = "${local.name}-igw" }
}

# --- Public subnets: things that must be reachable from the internet ------
resource "aws_subnet" "public" {
  count = length(local.azs)

  vpc_id                  = aws_vpc.main.id
  cidr_block              = local.public_subnet_cidrs[count.index]
  availability_zone       = local.azs[count.index]
  map_public_ip_on_launch = true

  tags = {
    Name                     = "${local.name}-public-${local.azs[count.index]}"
    "kubernetes.io/role/elb" = "1" # internet-facing load balancers go here
  }
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }

  tags = { Name = "${local.name}-public" }
}

resource "aws_route_table_association" "public" {
  count = length(local.azs)

  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}

# --- Private subnets: no route to the internet ----------------------------
resource "aws_subnet" "private" {
  count = length(local.azs)

  vpc_id            = aws_vpc.main.id
  cidr_block        = local.private_subnet_cidrs[count.index]
  availability_zone = local.azs[count.index]

  tags = {
    Name                              = "${local.name}-private-${local.azs[count.index]}"
    "kubernetes.io/role/internal-elb" = "1"
  }
}

resource "aws_route_table" "private" {
  vpc_id = aws_vpc.main.id

  # No routes: only the built-in "local" route inside the VPC.
  tags = { Name = "${local.name}-private" }
}

resource "aws_route_table_association" "private" {
  count = length(local.azs)

  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private.id
}

output "vpc_id" {
  value = aws_vpc.main.id
}

output "public_subnet_ids" {
  value = aws_subnet.public[*].id
}

output "private_subnet_ids" {
  value = aws_subnet.private[*].id
}
```

The new Terraform features in this file:

**`count`** creates several copies of one resource. With
`count = length(local.azs)` you get two subnets, addressed as
`aws_subnet.public[0]` and `aws_subnet.public[1]`. Inside the block,
`count.index` is `0` for the first copy and `1` for the second, so each copy
picks its own CIDR and AZ from the lists. Adding a third AZ means adding one
entry to each list, not copying a block.

**The splat expression `[*]`**: `aws_subnet.public[*].id` turns "all copies"
into a list of their IDs, for example `["subnet-0a1…", "subnet-0b2…"]`.
You will pass these lists to RDS now and to EKS later.

**`enable_dns_hostnames`** gives resources DNS names inside the VPC. RDS
endpoints are DNS names, so without it the application could not resolve the
database host.

**`map_public_ip_on_launch`** gives every instance started in a public subnet a
public IP, so the k3s server in the next chapter is reachable without extra
configuration.

**The `kubernetes.io/role/...` tags** are read by the AWS Load Balancer
Controller in Chapter 11: they tell it which subnets to use for internet-facing
and internal load balancers. They do nothing now, but adding them later would
change the subnets, so they are here from the start.

**`tags`** combine with the `default_tags` from `versions.tf` (Chapter 5): every
resource gets `Project` and `ManagedBy` automatically, and you only add `Name`.

## Step 3: Create the network

The VPC, subnets, route tables and internet gateway cost nothing, so you can
create them now and keep them. From `infra/terraform`:

```bash
terraform fmt && terraform validate && terraform plan
```

The plan should end with `Plan: 12 to add, 0 to change, 0 to destroy.`:
1 VPC, 1 internet gateway, 4 subnets, 2 route tables and 4 associations. Check
that the numbers add up before you apply; it is a habit worth building now,
while plans are short:

```bash
terraform apply
```

Check the result from the AWS side with one paste:

```bash
VPC=$(terraform output -raw vpc_id)
aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC \
  --query 'Subnets[].[Tags[?Key==`Name`]|[0].Value,CidrBlock,AvailabilityZone]' \
  --output table
aws ec2 describe-route-tables --filters Name=vpc-id,Values=$VPC \
  --query 'RouteTables[].[Tags[?Key==`Name`]|[0].Value,join(`, `,Routes[].DestinationCidrBlock)]' \
  --output table
```

You should see four subnets, and three route tables: `public` with
`10.0.0.0/16, 0.0.0.0/0`, `private` with only `10.0.0.0/16`, and one without a
name. That last one is the VPC's **main route table**, which AWS always
creates. Your subnets do not use it because each one is explicitly associated
with your own tables.

## Step 4: The database (`database.tf`)

The database needs three things besides the instance itself:

- a **DB subnet group**: the private subnets RDS may place the database in;
- a **security group**: a firewall attached to the database;
- an **ingress rule** on that security group: who may connect.

Create `infra/terraform/database.tf` and paste the whole file **except the
ingress rule**, which you type yourself below:

```hcl
resource "aws_db_subnet_group" "main" {
  name       = "${local.name}-db"
  subnet_ids = aws_subnet.private[*].id

  tags = { Name = "${local.name}-db" }
}

resource "aws_security_group" "db" {
  name        = "${local.name}-db"
  description = "PostgreSQL access from inside the VPC"
  vpc_id      = aws_vpc.main.id

  tags = { Name = "${local.name}-db" }
}

# (the ingress rule goes here)

resource "aws_db_instance" "main" {
  identifier     = "${local.name}-db"
  engine         = "postgres"
  engine_version = "16"
  instance_class = "db.t4g.micro"

  allocated_storage = 20
  storage_type      = "gp3"

  db_name  = "app"
  username = "app"

  # RDS generates the password and stores it in Secrets Manager.
  # It never appears in Terraform code or state.
  manage_master_user_password = true

  db_subnet_group_name   = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.db.id]
  publicly_accessible    = false

  # Practice settings: cheap and easy to throw away. Not for production.
  multi_az                = false
  backup_retention_period = 1
  deletion_protection     = false
  skip_final_snapshot     = true
  apply_immediately       = true
}

output "db_endpoint" {
  value = aws_db_instance.main.address
}

output "db_secret_arn" {
  value = aws_db_instance.main.master_user_secret[0].secret_arn
}
```

Now type the ingress rule in place of the comment:

```hcl
resource "aws_vpc_security_group_ingress_rule" "db_postgres" {
  security_group_id = aws_security_group.db.id
  description       = "PostgreSQL from the VPC"
  ip_protocol       = "tcp"
  from_port         = 5432
  to_port           = 5432
  cidr_ipv4         = aws_vpc.main.cidr_block
}
```

Read it as a sentence: *allow TCP on port 5432 into the database's security
group, from any address inside the VPC.* `cidr_ipv4` refers to the VPC instead
of repeating `"10.0.0.0/16"`, so the rule follows the VPC if its range ever
changes. A security group with no ingress rules allows nothing in; this rule is
the only door.

Two layers protect the database, and both would have to fail for it to be
exposed:

1. **The network.** It is in private subnets with no internet route, and
   `publicly_accessible = false` means it gets no public IP.
2. **The security group.** Even inside the VPC, only port 5432 is open.

A note on the separate rule resource: older examples put `ingress { ... }`
blocks inside `aws_security_group`. The AWS provider now recommends one
`aws_vpc_security_group_ingress_rule` per rule, because inline blocks and
separate rules fight over the same security group and produce endless plan
changes when mixed.

### The settings that matter

**`manage_master_user_password = true`** is the most important line. Without
it, you would have to put a password in a variable, and Terraform would store
it in plain text in the state file. With it, RDS generates a strong password,
stores it in **Secrets Manager** in a secret named `rds!db-<id>`, and rotates it
every 7 days. Terraform only knows the secret's ARN. The application reads the
password when it starts (Step 6).

**`engine_version = "16"`** pins the major version only. RDS chooses the newest
minor version and applies minor upgrades in the maintenance window.

**`db.t4g.micro`** is the smallest Graviton (ARM) instance and among the
cheapest. ARM does not matter to the application: it talks to PostgreSQL over
the network, not through compiled code.

**The practice settings** are the opposite of what production needs:

| Setting | Here | Production |
|---|---|---|
| `multi_az` | `false` | `true`: a standby in the second AZ takes over in about a minute |
| `backup_retention_period` | `1` day | 7–35 days |
| `deletion_protection` | `false` | `true`: blocks `destroy` until switched off |
| `skip_final_snapshot` | `true` | `false`: take a last snapshot on delete |
| `apply_immediately` | `true` | `false`: wait for the maintenance window |

They are chosen so that you can create and destroy the database freely during
practice. If you copy this file into a real project, change all five.

## Step 5: Create the database

```bash
terraform fmt && terraform validate && terraform plan
```

Expect `4 to add`: subnet group, security group, rule, instance. Then:

```bash
terraform apply
```

Creating an RDS instance takes **5 to 10 minutes**, sometimes longer. Terraform
prints `Still creating... [5m0s elapsed]` while it waits. This is normal; take
a break and let it finish. Do not press `Ctrl+C`.

When it completes:

```bash
terraform output
```

```text
db_endpoint = "rust-devops-db.abc123xyz.eu-central-1.rds.amazonaws.com"
db_secret_arn = "arn:aws:secretsmanager:eu-central-1:<ACCOUNT_ID>:secret:rds!db-1234abcd-...-AbCdEf"
private_subnet_ids = [ ... ]
public_subnet_ids = [ ... ]
vpc_id = "vpc-0abc..."
```

The endpoint is a DNS name. From your laptop it resolves to a private
`10.0.11.x` or `10.0.12.x` address that you cannot reach, which is exactly the
point. You will connect to it from inside the VPC in the next chapter.

## Step 6: How the application gets the password

Look at the secret without printing the password:

```bash
aws secretsmanager describe-secret \
  --secret-id "$(terraform output -raw db_secret_arn)" \
  --query '{Name:Name,Rotation:RotationEnabled,Days:RotationRules.AutomaticallyAfterDays,Owner:OwningService}'
```

The secret value is a small JSON document:

```json
{ "username": "app", "password": "a-long-random-string" }
```

The application expects one `DATABASE_URL`. The deploy script in Part IV
builds it on the server from three sources: the endpoint (from RDS), the
username and password (from Secrets Manager), and the database name. The
important part is this:

```bash
DATABASE_URL=$(SECRET_JSON="$SECRET_JSON" DB_HOST="$DB_HOST" DB_PORT="$DB_PORT" DB_NAME="$DB_NAME" python3 -c '
import json, os
from urllib.parse import quote
s = json.loads(os.environ["SECRET_JSON"])
print("postgres://{}:{}@{}:{}/{}?sslmode=require".format(
    quote(s["username"], safe=""), quote(s["password"], safe=""),
    os.environ["DB_HOST"], os.environ["DB_PORT"], os.environ["DB_NAME"]))
')
```

Two details in it each cost an evening of debugging in this project:

- **URL-encode the password.** Generated passwords contain characters such as
  `:`, `@`, `/` and `#`, which have a meaning inside a URL. A password with an
  `@` makes the URL parser think the host starts in the middle of the password.
  `quote(..., safe="")` turns them into `%3A`, `%40` and so on.
- **`?sslmode=require`.** RDS for PostgreSQL 15 and later only accepts
  encrypted connections by default (`rds.force_ssl = 1`). The application's sqlx
  dependency is built with the `tls-rustls` feature, so it can speak TLS; the
  URL parameter tells it to.

The value goes into a Kubernetes Secret, never into a file in Git and never
into the logs. The password is passed through environment variables instead of
command-line arguments, because arguments are visible to every user on the
machine in `ps`.

The server that runs this script also needs permission to read the secret.
That IAM policy belongs to the server, so it is created in the next chapter
together with the server's role.

## Step 7: Stop paying for the database

The network is free and can stay. The database costs money every hour it
exists, so destroy it at the end of every practice session:

```bash
terraform destroy -target=aws_db_instance.main
```

`-target` limits the operation to one resource. Terraform warns that this is
"not for routine use", and in a team that warning is right: targeted runs can
leave the state and the code out of step. Here it is a deliberate shortcut, and
the next `terraform apply` brings the database back. The subnet group and
security group stay; they are free.

Deleting the instance also deletes its secret. A recreated database has a new
password **and a new secret ARN**, which is why nothing in this project stores
either of them: the deploy script always looks them up fresh.

Put it in your routine:

```text
 start of session:  terraform apply                               (10 min)
 end of session:    terraform destroy -target=aws_db_instance.main (5 min)
```

## Troubleshooting

All of these happened while building this project.

**`terraform output` prints `No outputs found` or misses `db_endpoint`.**
Outputs are saved in the state during `apply`. Adding an `output` block and
running `plan` is not enough. Run `terraform apply` (it will show
"Changes to Outputs" and nothing else), then `terraform output` again.

**`DBSubnetGroupDoesNotCoverEnoughAZs`.** The subnet group had only one subnet.
RDS requires subnets in at least two AZs, even for a single-AZ database, so it
has somewhere to move to. This is why `local.azs` has two entries.

**An error that the instance class or an option is not available on the
free plan.** New AWS accounts on the free plan can only create small,
free-tier-eligible databases. Stay with `db.t4g.micro` (or `db.t3.micro`),
`multi_az = false` and 20 GB of storage, or upgrade the account plan.

**`no pg_hba.conf entry for host "10.0.1.23", user "app", database "app", no encryption`.**
The connection was not encrypted, and RDS rejects unencrypted connections.
Add `?sslmode=require` to the URL.

**`password authentication failed for user "app"` after recreating the database.**
The database is new, so its password is new. Something still used the old
`DATABASE_URL`: an old Kubernetes Secret, or a pod that started before the
change. Rerun the deploy script; it reads the current secret and restarts the
pods. The same happens after the automatic 7-day rotation.

**A database URL that fails to parse, with errors such as `invalid port number`.**
Special characters in the password were not URL-encoded. Build the URL with
`quote(..., safe="")` as in Step 6, never with string concatenation in bash.

**`terraform apply` seems to hang for minutes at the database.** It does not.
Creating, modifying and deleting RDS instances is slow. Check progress in the
console under **RDS → Databases**, where the status moves through `creating`,
`backing-up`, and `available`.

## What you learned

- How a VPC is divided into public and private subnets, and that a route table,
  not the subnet itself, decides which is which.
- How to read and plan CIDR ranges, and why ranges should not overlap.
- Why this design uses two AZs and no NAT gateway, and what production would
  do differently.
- How `count`, `count.index` and `[*]` create and reference several copies of a
  resource.
- How to put RDS in private subnets behind a security group with exactly one
  rule.
- How `manage_master_user_password` keeps the password out of code and state,
  and how the application gets it at deploy time (URL-encoded, with TLS).
- How to destroy only the expensive part with `-target`, and what changes when
  the database is recreated.

## Practice

Each exercise says how long it takes and how much you type.

1. **The `count` trap** (15 min, edit 2 lines). Add `"eu-central-1c"` to the
   **start** of `local.azs`, and `"10.0.3.0/24"` / `"10.0.13.0/24"` to the start
   of the CIDR lists. Run `terraform plan` (do not apply). Why does Terraform
   want to replace subnets you did not change? Move the new entries to the
   **end** of the lists and plan again. Revert the change afterwards. (This is
   why many teams use `for_each` with a map instead of `count` for things that
   might be reordered.)
2. **Explore with `terraform console`** (10 min, type 4 short lines). Run
   `terraform console` and try `aws_subnet.private[*].cidr_block`,
   `cidrsubnet("10.0.0.0/16", 8, 11)`, `length(local.azs)` and
   `aws_db_instance.main.address`. Type `exit` to leave.
3. **Calculate the subnets** (15 min, edit 2 lines). Replace the two
   hard-coded CIDR lists with expressions using `cidrsubnet()` and `range()`, so
   that the subnets follow from the VPC range. The plan must show
   `No changes.` when you are done; that proves the expressions produce the
   same values.
4. **Rotation** (10 min, paste only). Run the `describe-secret` command from
   Step 6. How often is the password rotated? Think about what happens to a pod
   that is still running with the old password after a rotation, and how you
   would handle it. (Hint: existing connections stay open; new ones fail.)
5. **Recreate the database** (20 min including waiting, paste only). Note the
   current `db_secret_arn`, run the destroy from Step 7, then `terraform apply`
   again, and compare the ARN. Then destroy the database again.

Finish the session with `terraform destroy -target=aws_db_instance.main`.
